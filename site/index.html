Remote Desktop Rider

Fast, private 1:1 remote desktop for Windows that stays usable on bad connections.

Help a family member, reach your office PC from home, or support a customer: over mobile data, hotel Wi-Fi, a strict company firewall or a slow VPN.

Download for Windows View on GitHub

Other systems

Free and open source. Control from Windows, macOS or Linux; the computer you control runs Windows 10/11. No accounts, no cloud.

Features

Built for the connection you actually have

  • Smooth on poor networks

    QUIC over UDP, hardware H.264 (QuickSync / NVENC / AMF), a locally drawn cursor, stale frames dropped instead of resent, and live adaptive bitrate (300 kbps–20 Mbps).

  • Quality you can pick

    Auto / 1080p / 720p / 480p in the session toolbar. Auto lowers the resolution on slow connections and raises it again when the link recovers.

  • Private by design

    Devices pair once by comparing a code. Every session is end-to-end encrypted and needs the computer's PIN. No accounts, no cloud.

  • Gets through firewalls

    Direct on the LAN, NAT hole punching or an encrypted relay across the internet. Falls back to a random UDP port, then to an HTTPS (TCP 443) tunnel through the system proxy.

  • Works everywhere on the host

    Login screen, lock screen, UAC prompts and after a restart.

  • Everyday tools

    Text clipboard sync both ways, drag-and-drop files to the host, multi-monitor switching, Ctrl+Alt+Del, lock the remote PC, restart it and reconnect when it is back, wake a sleeping PC over its wired network.

  • Self-hosted

    The optional rider-server runs on any small Linux machine. It introduces devices and relays encrypted traffic; it can't watch or take over sessions.

  • Keeps itself current

    Hourly update checks, SHA-256 verified installers, unattended updates for PCs you only reach remotely.

  • Small and native

    Native apps for each system; the Windows installer is about 8 MB. Rust end to end.

  • English and Azerbaijani

    The app, the session window and the Manage window are available in English and Azerbaijani. Switch with the flag buttons in the app's sidebar or in Settings.

How it works

Pair once, then connect with a PIN

Install Remote Desktop Rider on both computers (see Download). The computer you control needs Windows; you can control it from Windows, macOS or Linux. Pairing happens once per device; after that, every session needs the computer's PIN.

  1. 1

    On the computer to control

    Open This computer → Manage this computer, set a PIN, turn on remote access and click Add a device. It shows a short code.

  2. 2

    On your device

    Click Add computer, enter that code and check that both screens show the same verification code.

  3. 3

    Connect

    Once the computer is online, click Connect and enter the PIN. Tick Remember PIN on this device and later connections open straight away, like unattended access in other tools (on Windows, the PIN is encrypted for your Windows account). The remote computer shows a red banner while someone is connected; clicking it ends the session.

To pair and connect across networks, set your rider-server address and fingerprint once per computer: on Windows in This computer → Manage this computer → Server, on macOS and Linux in Settings → Server (see Self-host your server). Without a server, devices on the same network can still pair by address.

New

Quick connect with a one-time code

For one-off help, not long-term access. No admin rights, no PIN, no pairing.

  1. Person who needs help

    Opens Remote Desktop Rider and, on the This computer page, clicks Get a one-time code.

  2. Helper

    Clicks Quick connect and enters that code.

  3. Person who needs help

    Sees who wants to connect plus a verification code, and clicks Allow (or Decline).

  • The code looks like SF6-CK6 (6 letters and digits, issued by your server). It works once and is valid for 10 minutes.
  • Quick connect needs the server to be set (Windows: This computer → Manage this computer → Server; macOS and Linux: Settings → Server).
  • Nothing is remembered after the session.
  • The helper's view ends when either side closes it; the red banner on the remote screen ends it too.

Limitation: a quick session runs without admin rights, so windows running as administrator and UAC prompts can't be controlled. For that, use the regular paired access.

How it connects

Direct when it can, relay when it must, HTTPS when nothing else gets through

  1. Direct. On the same network, or across the internet once the server has helped both sides punch through their NATs. LAN addresses are tried first.
  2. Relay. When no direct path works, the session goes through the server's UDP relay.
  3. HTTPS tunnel. Where no UDP gets through at all (some company networks), both sides carry their traffic inside a WebSocket over HTTPS on port 443, through the system proxy, like a browser. Sessions then use the relay.

On every path the session is end-to-end encrypted with the keys pinned at pairing. The server and relay only see ciphertext. If the host's usual UDP port 47800 is filtered, it also uses a second, random high port. If the server is down, a known direct address is still tried. The viewer shows which path it chose.

Security

No accounts, no cloud, no central point to compromise

  • Device keys, pinned at pairing

    Every device has its own Ed25519 identity key. There is no CA and no central server that could be compromised to impersonate a host.

  • Pairing confirmed on both sides

    Both screens show a 6-digit verification code derived from both keys and the live TLS session. A man-in-the-middle would produce different codes.

  • Mutual TLS

    The host rejects unpaired devices during the TLS handshake, before any application code runs. The client refuses a host whose key changed.

  • A PIN for every session

    Argon2id-hashed, exponential back-off, locked for 15 minutes after 10 failures. A stolen client laptop is not enough on its own.

  • One session at a time

    A red banner on the host while someone is connected. The banner is hidden from the stream; clicking it ends the session.

  • The server sees only ciphertext

    It can't watch, take over or impersonate a host. It answers the same "offline or not allowed" to everyone not paired with a host and rate-limits requests per IP.

  • Locked-down files

    The host's private key and trust store live in %ProgramData%\RemoteDesktopRider, readable only by SYSTEM and Administrators.

  • Verified updates

    Every download is checked against the SHA-256 published with the release. Automatic updates can be turned off.

Enterprise

Every computer in the company, one admin, nobody watched without consent

Enterprise mode lets one IT admin look after a company's Windows PCs from the app: arranged by floor and room, searchable, connected with a double-click. It runs on your own rider-server, like everything else.

  • Rolled out by Group Policy

    A startup script installs Remote Desktop Rider on every domain PC and joins it to the company with a token. New PCs appear under Unassigned; drag them to their room.

  • The employee decides

    Each connection asks the person at the computer to Accept or Decline. No answer within a minute, a locked screen or nobody signed in: no session.

  • Unattended only when both agree

    Access without asking needs the installer's /UNATTENDED switch and the admin's switch for that PC. Either one alone is not enough.

  • One admin, pinned

    The admin signs in once with a one-time setup code. Company PCs trust only that admin's device key; other devices can't list or reach them.

  • Office or remote at a glance

    A laptop working from home over the company VPN, such as GlobalProtect, is marked Remote. Each PC tells by itself: its Windows domain on its own network means the office.

Self-host your server

Your own server in one line

Without a server, devices reach each other only on the same network, over a VPN or through a port forward. To connect from anywhere, run the small rider-server on any Linux machine both sides can reach. A cheap VPS is plenty.

curl -fsSL https://codewithelvin.github.io/remote-desktop-rider/install.sh | sudo bash -s -- <public-ip>

  • Installs or upgrades rider-server (Linux x86_64, systemd) from the latest GitHub release.
  • Verifies its SHA-256.
  • Opens UDP 47900 and 47901–47999 in ufw.
  • Keeps the server key across upgrades, so the fingerprint never changes.
  • Prints the fingerprint.

<public-ip> is optional, except behind cloud NAT.

Optional: HTTPS fallback for networks that block UDP

Add --domain rider.example.com --email you@example.com to also set up nginx and a Let's Encrypt certificate. This needs TCP 80 and 443 open and the DNS name pointing at the server.

curl -fsSL https://codewithelvin.github.io/remote-desktop-rider/install.sh | sudo bash -s -- <public-ip> --domain rider.example.com --email you@example.com

Then, on every computer

Enter the server address and fingerprint: on Windows in This computer → Manage this computer → Server, on macOS and Linux in Settings → Server. It applies in both directions: being reached and reaching others.

FAQ

Troubleshooting

Windows says “Unknown publisher”

The installer isn't code-signed yet, so SmartScreen may warn. Click More info → Run anyway. To verify the download, compare its SHA-256 with the line for that file in SHA256SUMS on the release page (in PowerShell: Get-FileHash rdr-setup-x.y.z.exe).

macOS says the app can't be opened

The app isn't signed with an Apple Developer ID yet, so macOS blocks the first launch. Open System Settings → Privacy & Security and click Open Anyway next to the message about Remote Desktop Rider, then confirm. Or right-click the app in Applications and choose Open. You only need to do this once.

No code appears when I click "Add a device"

The code comes from your server. Set the Server in This computer → Manage (address and fingerprint), then try again. Without a server, only devices on the same network can add this computer, using one of the addresses the dialog shows.

It doesn't connect from a company network

This is handled automatically when the server is set up for it. If UDP 47800 is filtered, the host uses a random high port. If no UDP gets through at all, both sides switch to the HTTPS tunnel on TCP 443 through the system proxy. That needs nginx with a real certificate on the server (the --domain option above sets it up).

The picture is blurry or choppy

On Auto, quality follows the connection. Pick a fixed resolution in the toolbar's quality menu if you prefer: 720p or 480p often feels smoother on a weak link. The title bar shows round-trip time and latency.

Win+L locks my own PC, not the remote one

Windows reserves Win+L (and Ctrl+Alt+Del) for the local computer. Use Ctrl+Alt+Shift+L to lock the remote computer, and Ctrl+Alt+End or the toolbar for Ctrl+Alt+Del.

I can't click an administrator window during a quick connect session

Quick connect runs without admin rights, so windows running as administrator and UAC prompts can't be controlled. Use the regular paired access for that.
